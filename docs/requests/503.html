Typed product envelope: how big, how heavy

Phase 1 of todo/DIMENSIONS.md. Every product now carries a comparable physical envelope: length, width and height normalised to mm, weight to kg, and a derived largest dimension you can sort and filter on across vendors. Before this, 40% of stored dimensions were inches, the unit was free text, and nothing could be compared.

▮▮▮ WHAT'S IN THE BOX ▮▮▮
  1. E-1

    Per-axis dimensions in mm

    ProductBase.dimensions is now {length, width, height}, each a {value, unit: "mm"}. The legacy {floats…, unit} shape still loads. Axes that are ≤0, non-finite, over 20 m or in a non-length unit become None. One bad axis never kills the row.

  2. E-2

    Weight in kg, largest dimension derived

    lb / lbs / g / oz convert to kg. max_dimension is recomputed from the axes on every validation. It is never asked of the LLM and never counted toward extraction quality.

  3. E-3

    Conditional migration

    ./Quickstart admin normalize-envelope --stage dev|staging [--apply] sends one UpdateItem per row and touches only the three envelope attributes. A condition on the old values skips rows a concurrent writer changed. It refuses prod. Dev dry run: 9,502 of 37,263 rows to rewrite, 653 empty {unit} stubs dropped.

  4. E-4

    Largest Dimension + Weight columns

    Every curated product type gets both columns, placed in COLUMN_ORDER. Filter chips start at < because you spec a ceiling for cabinet space or payload. A column shows once 25% of the loaded rows have a value.

Coverage is the next problem. Phase 2 backfills the envelope from outline-drawing pages. Phase 3 adds exact interface geometry (shaft, collet bore, threads, pilot, bolt circle): a value is stored only when a standard table and the drawing agree, or two independent reads agree. Otherwise it is withheld and the UI links to the drawing page.
